## Request and transport inspection

The report names `models/gemini-3.5-flash-lite` and input/output caps of 16,384/1,024. At inspection, the local configuration uses that model, API `v1beta`, 1,024 output tokens, temperature 1.0, `MINIMAL` thinking, a 30-second per-operation HTTP timeout, verified TLS, no environment proxies or redirects, and zero retries. The historical report did not retain all settings or the exact request bodies, request IDs, timestamps or provider error envelopes; the current configuration and source cannot prove that every setting was identical during the earlier run.

The current code builds every request through the same canonical preparation path: system instruction, question and selected evidence, one-candidate generation configuration and structured response schema. The question, selected evidence and citation-ID enum vary between requests. Counting wraps the full prepared request; generation sends its same model through `POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.5-flash-lite:generateContent`. The request-bound approval checks the counted request before generation. A successful count shows the input gate approved that request, not that generation must succeed. There is no automatic retry or model fallback.

Google's [GenerateContent API error reference](https://ai.google.dev/gemini-api/docs/generate-content/api-errors) says HTTP 503/`UNAVAILABLE` may indicate temporary service overload or unavailability, while 429/`RESOURCE_EXHAUSTED` is the documented rate-limit category. The historical report recorded HTTP 503 only; it did not retain the structured status or reason. This is compatible with capacity pressure, but it does not prove an outage or identify the cause of these particular responses. Google recommends bounded backoff for transient failures in its [troubleshooting guide](https://ai.google.dev/gemini-api/docs/troubleshooting); this experiment deliberately retains one attempt and zero retries.

Google's [Gemini 3 GenerateContent guide](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.5) says to remove `candidate_count` for Gemini 3.x, whereas the present request sets `candidateCount` to 1. This is a compatibility item for separate review, not a demonstrated explanation for the 503s: successful and failed results were produced by the same reported model, and the report lacks the exact prior requests. No request settings were changed in this diagnostic step. Google's [thinking documentation](https://ai.google.dev/gemini-api/docs/generate-content/thinking) lists `minimal` as supported for Gemini 3.5 Flash-Lite.

## Added diagnostic behavior

For a non-200 response, the transport captures only bounded, sanitized metadata: numeric provider error code; canonical status; allowlisted `google.rpc.ErrorInfo` reasons; a validated `Retry-After`; and a restricted-format provider request or trace ID from recognized headers. It retains at most 8,192 bytes of an identity-encoded JSON error body, reading in 1,024-byte chunks and discarding an oversize body; it ignores message text, arbitrary metadata, non-JSON and malformed bodies. Unrecognized or absent values are reported as `unknown`; safe data may therefore be omitted. The evaluation report also records the existing content-bound application request ID when a count receipt is available. No raw response body, request/evidence body, credentials or headers are printed in diagnostics. Diagnostic extraction cannot replace or mask the original HTTP status error and adds no provider calls or retries.

The one-question file is `data/evaluation/device_incident_single_question.json`. The single live attempt has not been run in this review.
