Without that material, a model has less explicit evidence for stating when those other provisions apply. The general v6 prompt mentioned conditional reporting and communication but did not explicitly ask it to connect a potentially qualifying recall with reporting timing and the field safety notice. This is an evidence-and-instruction gap, not proof of why the model made its particular choice.

## Gemini candidateCount compatibility

Google's [Gemini troubleshooting guide](https://ai.google.dev/gemini-api/docs/troubleshooting) says candidate count is unsupported on Gemini 3, while its generic [GenerateContent examples](https://ai.google.dev/api/generate-content) show it for a Gemini 3 model. Google's [v1beta service definition](https://github.com/googleapis/googleapis/blob/master/google/ai/generativelanguage/v1beta/generative_service.proto) describes the optional field as defaulting to one. Given this documentation inconsistency, the application follows the explicit model-family guidance and now omits the field from the complete logical request; both the count and generation bodies derive from that same request. The existing response parser still rejects anything other than exactly one candidate. The request format is now `mdr-gemini-request/v2`, and both the format and changed request payload affect the request ID, preventing reuse of an old approval. This addresses the field-construction compatibility item offline; it does not establish that the field caused the prior 503s or prove live provider behavior.

The existing request-budget and scope policies remain in force. Model compliance with the new instructions, source-supported recall details, token count and any provider availability issue require the user's one-question live review.
